# ADR-035: Auto-discovery schedule set in the Mini App

- **Status:** Accepted
- **Date:** 2026-10-28
- **Related:** REQ-003 · replaces the fixed 03:00 timer in the spec's deployment section

## Context

Discovery ran once a day at 03:00 VPS time, fixed in `clipforge-discovery.timer`. Administrators want to turn the daily run off or move it to another hour from Settings. The API runs as the unprivileged `clipforge` user under `ProtectSystem=strict`, so it cannot rewrite or reload systemd units, and granting it that would undo the service hardening.

## Decision

- `discovery` settings gain `auto_enabled` (default `true`) and `auto_hour` (0–23, default `3`, VPS time zone). The defaults keep the previous behavior, so no migration is needed.
- `clipforge-discovery.timer` fires `hourly` and keeps `Persistent=true`. Its service runs `python -m clipforge.discovery_cli --scheduled`.
- With `--scheduled` the CLI reads the settings and exits 0 without calling YouTube unless auto-discovery is enabled and the current local hour equals `auto_hour`. Without the flag the CLI runs unconditionally, as before.
- Manual runs (Sources → Run discovery now, `POST /discovery/run`) ignore both settings.

## Consequences

- Changing the schedule takes effect at the next hourly tick, with no deploy or `systemctl` step.
- The timer starts the service 24 times a day; 23 of those only read one settings row and exit.
- Catch-up after downtime is weaker: a run missed while the VPS was down is caught up at boot only if boot happens within the configured hour.
- `systemctl start clipforge-discovery.service` no longer forces a run outside the configured hour; operators run the CLI without `--scheduled` instead (runbook).
- Disabling `clipforge-discovery.timer` in systemd still stops all scheduled runs, whatever the settings say.
